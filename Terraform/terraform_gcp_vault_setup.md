# Terraform + HashiCorp Vault + GCP — Step‑by‑Step Setup

---

## 0) What you’ll build

- A **secure pipeline** where Terraform retrieves secrets from **HashiCorp Vault** to provision resources in **Google Cloud (GCP)**.
- Two ways to authenticate the Google provider via Vault:
  1) **KV (static) secret** → a stored Service Account (SA) JSON.
  2) **Dynamic secrets** → short‑lived OAuth access token or ephemeral SA key generated by Vault’s **GCP Secrets Engine**.

**Architecture:**

```
Terraform (local/CI) ──(AppRole/JWT)──> Vault
     │                    ├─ KV v2 (static SA JSON)
     │                    └─ GCP Secrets Engine (dynamic, short‑lived)
     └────────(google provider)────────> GCP APIs
```

---

## 1) Prerequisites

- **Terraform** ≥ 1.5
- **Vault** ≥ 1.13 (server reachable at `VAULT_ADDR`)
- **GCP** project where you can create a test bucket
- CLIs installed: `vault`, `gcloud`, `jq`
- A GCP Service Account with **admin/minting rights** to generate tokens/keys for Vault dynamic secrets (export this key as JSON → `vault-gcp-admin.json`).

> **Environment variables to export** (adapt to your setup):
```bash
export GCP_PROJECT_ID="your-project-id"
export REGION="us-central1"

export VAULT_ADDR="https://vault.example.com"  # or http://127.0.0.1:8200
# For initial admin operations you need an admin/root token:
export VAULT_TOKEN="hvs.xxxxxxxxx"             # use only on admin machine
```

---

## 2) Vault — Enable Engines

Run with an **admin Vault token** (NOT used by Terraform later).

```bash
# Enable KV v2 for static secrets (if not already)
vault secrets enable -path=secret kv-v2 || true

# Enable GCP secrets engine for dynamic secrets (if not already)
vault secrets enable gcp || true
```

---

## 3) Vault — Configure GCP Secrets Engine (Dynamic)

### 3.1 Configure Vault with a GCP “admin” SA key
This SA lets Vault mint short‑lived creds.

```bash
vault write gcp/config credentials=@vault-gcp-admin.json
```

### 3.2 Create roles (one for tokens, one for ephemeral keys)

```bash
# Short‑lived OAuth access token (cloud‑platform scope)
vault write gcp/roleset/tf-access-token \
  project="${GCP_PROJECT_ID}" \
  secret_type="access_token" \
  token_scopes='["https://www.googleapis.com/auth/cloud-platform"]'

# Ephemeral service account key (bind required roles to the generated SA)
vault write gcp/roleset/tf-ephemeral-key \
  project="${GCP_PROJECT_ID}" \
  secret_type="service_account_key" \
  bindings=@- <<'JSON'
{
  "roles/storage.admin": [
    "serviceAccount:__service_account_email__"
  ]
}
JSON
```
> Adjust roles/bindings to least privilege for your use case.

---

## 4) (Optional) Vault — Store a Static SA Key in KV

If you must use a long‑lived SA JSON (not recommended for prod):

```bash
# `sa-key.json` is the GCP Service Account JSON you downloaded
vault kv put secret/gcp/sa-key creds=@sa-key.json
```

---

## 5) Vault — Policies (Least Privilege)

Create two policy files locally:

**`policy-kv-read.hcl`** (read‑only access to one KV path)
```hcl
path "secret/data/gcp/sa-key" {
  capabilities = ["read"]
}
```

**`policy-gcp-access.hcl`** (read dynamic secrets from rolesets)
```hcl
# OAuth token lease
path "gcp/token/tf-access-token" {
  capabilities = ["read"]
}

# Ephemeral key lease
path "gcp/key/tf-ephemeral-key" {
  capabilities = ["read"]
}
```

Apply them to Vault:
```bash
vault policy write terraform-kv-read policy-kv-read.hcl
vault policy write terraform-gcp-access policy-gcp-access.hcl
```

---

## 6) Vault — Auth Method for Terraform (AppRole)

Enable AppRole if needed:
```bash
vault auth enable approle || true
```

Create an AppRole with the policies you need:
```bash
vault write auth/approle/role/terraform \
  token_policies="terraform-kv-read,terraform-gcp-access" \
  token_ttl=1h token_max_ttl=4h \
  secret_id_ttl=1h secret_id_num_uses=1
```

Fetch **RoleID** and **SecretID** (save for CI/locals, never commit):
```bash
vault read -field=role_id auth/approle/role/terraform/role-id
vault write -field=secret_id -f auth/approle/role/terraform/secret-id
```

## 7) Terraform Project — Files

Create a folder, e.g., `terraform/`, and these files:

```
terraform/
├─ versions.tf
├─ providers.tf
├─ variables.tf
├─ main_kv_static.tf            # Option A: KV static SA JSON
├─ main_dynamic_access_token.tf  # Option B1: dynamic OAuth token
├─ main_dynamic_key.tf           # Option B2: dynamic ephemeral SA key
├─ outputs.tf
└─ terraform.tfvars
```

### 7.1 `versions.tf`
```hcl
terraform {
  required_version = ">= 1.5"
  required_providers {
    vault = {
      source  = "hashicorp/vault"
      version = ">= 4.3.0"
    }
    google = {
      source  = "hashicorp/google"
      version = ">= 5.32.0"
    }
  }
}
```

### 7.2 `providers.tf` (Vault via AppRole)
> Use environment variables to avoid secrets in code.

```hcl
provider "vault" {
  # Uses: VAULT_ADDR, VAULT_APPROLE_ROLE_ID, VAULT_APPROLE_SECRET_ID
}

# Choose ONE of the google providers below in your plan/apply (comment others)
```

### 7.3 `variables.tf`
```hcl
variable "project_id" {
  description = "GCP Project ID"
  type        = string
}

variable "region" {
  description = "Default region"
  type        = string
  default     = "us-central1"
}
```

### 7.4 **Option A — KV Static** (`main_kv_static.tf`)
```hcl
# Read KV v2 secret with SA JSON
data "vault_kv_secret_v2" "gcp_sa" {
  mount = "secret"
  name  = "gcp/sa-key"
}

provider "google" {
  project     = var.project_id
  region      = var.region
  credentials = data.vault_kv_secret_v2.gcp_sa.data["creds"]  # JSON string
}

resource "google_storage_bucket" "kv_demo" {
  name          = "tf-kv-demo-${var.project_id}"
  location      = "US"
  force_destroy = true
}
```

### 7.5 **Option B1 — Dynamic OAuth Token** (`main_dynamic_access_token.tf`)
```hcl
# Ask Vault for a short‑lived OAuth token
data "vault_gcp_access_token" "tf" {
  role = "tf-access-token"
  # scopes can be overridden if needed
  # scopes = ["https://www.googleapis.com/auth/cloud-platform"]
}

provider "google" {
  project      = var.project_id
  region       = var.region
  access_token = data.vault_gcp_access_token.tf.token
}

resource "google_storage_bucket" "dyn_token_demo" {
  name          = "tf-dyntoken-demo-${var.project_id}"
  location      = "US"
  force_destroy = true
}
```

### 7.6 **Option B2 — Dynamic Ephemeral Key** (`main_dynamic_key.tf`)
```hcl
# Request an ephemeral SA key (base64 JSON)
data "vault_gcp_service_account_key" "tf" {
  role = "tf-ephemeral-key"
}

locals {
  sa_key_json = base64decode(data.vault_gcp_service_account_key.tf.private_key_data)
}

provider "google" {
  project     = var.project_id
  region      = var.region
  credentials = local.sa_key_json
}

resource "google_storage_bucket" "dyn_key_demo" {
  name          = "tf-dynkey-demo-${var.project_id}"
  location      = "US"
  force_destroy = true
}
```

### 7.7 `outputs.tf`
```hcl
output "bucket_names" {
  description = "Created buckets"
  value = compact([
    try(google_storage_bucket.kv_demo.name, null),
    try(google_storage_bucket.dyn_token_demo.name, null),
    try(google_storage_bucket.dyn_key_demo.name, null)
  ])
}
```

### 7.8 `terraform.tfvars`
```hcl
project_id = "YOUR_GCP_PROJECT_ID"
region     = "us-central1"
```

**.gitignore** should include: `*.tfvars`, `.terraform/`, and NEVER commit secrets.

## 8) Run — Local or CI

Pick **one** main file at a time (comment out the other two).

```bash
cd terraform

# Vault auth via AppRole (do NOT use admin/root token here)
export VAULT_ADDR="https://vault.example.com"
export VAULT_APPROLE_ROLE_ID="YOUR_ROLE_ID"
export VAULT_APPROLE_SECRET_ID="YOUR_SECRET_ID"

terraform init
terraform plan  -var="project_id=${GCP_PROJECT_ID}"
terraform apply -auto-approve -var="project_id=${GCP_PROJECT_ID}"
```

You should see one bucket created depending on the option selected.

---

## 9) Rotate & Revoke

- **Dynamic** creds auto‑expire (lease/TTL). To revoke early:
```bash
vault lease revoke <lease_id>
```

- **KV static**: rotate by writing a new SA key:
```bash
vault kv put secret/gcp/sa-key creds=@new-sa-key.json
```

---

## 10) Security Best Practices

- Prefer **dynamic** secrets for CI/CD (short‑lived, revocable).
- Lock Vault **policies** to exact paths.
- Use **AppRole** or **OIDC/JWT** for Terraform → Vault (no long‑lived tokens).
- Scope TTL and `secret_id_num_uses` tightly.
- Avoid printing secrets; keep them out of VCS and logs.
- Use a secure Terraform **remote state** backend (GCS with CMEK, S3+KMS, Terraform Cloud, etc.).

---

## 11) Troubleshooting

- **403 from GCP**: verify IAM bindings/roles and token scopes.
- **Vault `permission denied`**: check AppRole policies cover exact paths.
- **`no such path`**: validate engine and role paths (`gcp/token/<role>`, `gcp/key/<role>`, `secret/data/...`).
- **`google: could not find default credentials`**: ensure you set either `access_token` **or** `credentials` in the Google provider.
- **CI fails to auth to Vault**: confirm network access, `VAULT_ADDR`, and valid AppRole secrets.

---

## 12) What Vault Actually Stores

- **KV static**: your uploaded SA JSON (`sa-key.json`) — encrypted at rest.
- **Dynamic**: leases for issued **OAuth tokens** or **ephemeral SA keys**. Tokens/keys expire automatically and can be revoked early.

**Rule of thumb:** KV = **you store** it. Dynamic = **Vault generates** it (safer).
